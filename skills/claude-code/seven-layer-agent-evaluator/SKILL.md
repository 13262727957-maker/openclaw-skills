# 七层模型 Agent 问答测评器

## 目的

使用本技能进行“用户提问，Agent 回答，最后 Agent 自评”的七层模型理解测试。

这不是让 Agent 预先设计一套考试题，而是由用户直接提问。Agent 每轮都要基于七层模型回答，并在测试结束时回顾自己的表现：

- 回答是否准确理解了 M1-M7。
- 是否把问题映射到了正确对象、动作、规则、场景、权限、补偿和护栏。
- 是否读取了正确的模型文件。
- 是否在需要时安全调用 API 或操作前端页面。
- 是否遵守只读、`prepare_only`、人工确认等执行边界。
- 是否能说明自己的不确定性和模型缺口。

默认模式是问答测评。用户可以随时说“开始测试”“继续问”“结束测试并总结”“给我自评报告”。

详细记录格式和报告模板见 [references/evaluation-contract.md](references/evaluation-contract.md)。

## 测试开始时

当用户要测试 Agent 对七层模型的理解时，先建立测评上下文：

1. 确认七层模型入口。
   - 如果用户给了目录，优先读取总览 MD、Agent 可读 JSON、知识图谱 JSON。
   - 如果用户只说“用当前七层模型”，优先尝试当前工作区的 `M1-M7总体汇总.md`、`agent-readable/m1-m7-agent-summary.json`、`knowledge-graph/m1-m7-kg-summary.json`。
   - 不要一次性读取所有原始证据文件；按问题需要逐步读取。

2. 确认允许的操作级别。
   - 默认允许模型文件读取。
   - API、数据库、前端页面只读操作需要用户已提供授权和环境。
   - 写动作默认 `prepare_only`。
   - 破坏性动作、审批、提交、取消、推送外部系统等动作默认不执行，只能说明方案或准备请求。

3. 初始化会话记录。
   - 记录开始时间。
   - 记录模型入口文件。
   - 每个用户问题形成一个 `questionRecord`。
   - 最终自评基于这些记录生成。

不要把账号密码、cookie、token、会话值写入记录或报告。

## 每轮回答流程

每收到一个用户问题，按以下流程处理：

1. 判断问题类型。
   - `business_understanding`：解释业务对象、流程、状态、规则。
   - `model_location`：指出信息在哪一层、哪个文件、哪个字段。
   - `action_routing`：把用户意图映射到 M2 动作/API/前端动作。
   - `rule_check`：判断动作是否满足 M3/M5-M7 条件。
   - `data_analysis`：基于数据库/API/页面返回分析数据。
   - `operation_plan`：准备查询、新增、修改、删除、审批、推送等操作方案。
   - `execution_request`：用户要求实际调用 API 或操作页面。
   - `gap_review`：判断模型缺口或 Agent 回答缺口。

2. 选择需要调用的层。
   - M1：对象、字段、状态、业务键、表关系。
   - M2：动作、参数、API、前端行为。
   - M3：前置规则、状态转换、数量/追溯/必填/阻断。
   - M4：业务链步骤、前后动作、外部系统位置。
   - M5：登录态、租户、组织、角色、菜单、按钮、数据权限。
   - M6：失败类型、重试、回滚、补偿、外部系统影响。
   - M7：幂等、重查、人工确认、审计、执行后校验、安全策略。

3. 读取必要资料。
   - 优先使用已经读取过的七层模型摘要。
   - 只有问题需要完整字段、完整动作参数或图谱关系时，再读取细分 JSON。
   - 如果要调用 API/页面/数据库，先确认是否在允许范围内，并遵守 M5-M7。

4. 回答问题。
   - 先给直接结论。
   - 再说明使用了哪些层。
   - 涉及执行时，必须说明读写级别和安全边界。
   - 不确定时明确标注“不确定/模型缺口/需要运行数据确认”，不要编造。

5. 记录本轮表现。
   - 记录问题、问题类型、使用层、读取文件、工具/API/页面调用、是否执行写操作、耗时、置信度、是否有未确认点。
   - 如果回答后发现自己前后矛盾，应在下一轮或最终报告中承认并修正。

## API 和前端操作规则

只在用户授权且模型允许时操作：

- 只读 API：可以在具备登录态、参数、权限边界时调用。
- 前端只读：可以执行查询、筛选、详情查看、打印/导出准备等非破坏性操作。
- 写动作：默认只准备请求体、校验清单、确认文案和回滚方案。
- 高风险写动作：新增、修改、删除、提交、审批、弃审、取消、质检完成、推送 OA/U9/QMS 等，必须按 M5-M7 做权限、补偿、幂等、重查、人工确认。
- 如果模型标注 `prepare_only`，不能实际执行写 API。

如果用户的问题是在测试理解能力，而不是要求真实操作，优先回答“我会怎么做”和“为什么”，不要贸然调用接口。

## 结束测试时

当用户说“结束测试”“给我总结”“生成测评报告”“自评一下”时，输出自评报告。

报告必须包含：

- 测试范围和使用的模型入口。
- 问答总数、总耗时、平均耗时。
- 每轮问题的简表：问题、类型、调用层、是否查文件、是否调工具/API/前端、结果。
- 分层自评：M1-M7 各层理解情况。
- 能力自评：业务理解、动作路由、规则应用、场景推理、执行安全、工具使用、表达清晰度。
- 错误和不确定项：哪些是 Agent 自身问题，哪些是模型缺口，哪些是运行环境缺口。
- 可执行能力判断：可自动只读、只能 prepare_only、必须阻断。
- 下一步建议：模型需要补什么、Agent 测试还应问什么、运行器安全能力是否需要补。

## 评分规则

使用 0-5 分：

- `0`：未回答、答反、或存在明显危险。
- `1`：大部分错误，无法基于模型执行。
- `2`：有部分模型依据，但遗漏关键层或安全条件。
- `3`：基本正确，可以解释业务，但执行级细节不足。
- `4`：正确、有模型依据，能说明安全边界，仅有小缺口。
- `5`：准确、完整、跨层关联清楚，并能安全指导 API/前端操作。

评分时不要只看回答是否流畅，要重点看：

- 是否引用了正确层。
- 是否把业务对象、动作、规则、场景、安全护栏连起来。
- 是否避免编造。
- 是否遵守 M5-M7。
- 是否能把“模型缺口”和“Agent 没答好”区分开。

## 输出原则

- 回答用户问题时保持自然，不要每轮都输出完整评分表，除非用户要求。
- 在测试过程中可以简短说明“本题我用到 M1/M2/M3”。
- 最终报告再集中输出完整记录和自评。
- 不输出敏感凭证、cookie、token、长日志或无关扫描证据。
